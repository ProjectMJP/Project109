## 1. Git 및 GitHub 작업 규칙
- 코드를 변경하거나 커밋/푸시를 수행할 때는 **절대 GitHub MCP 도구를 직접 임의로 판단해서 연속 호출하지 마라.**
- 반드시 `git-commit-helper` 스킬(`/.agents/skills/git-commit-helper/SKILL.md`)의 절차와 가이드를 트리거하여 작업을 수행해야 한다.
- 코드 개발 및 변경 작업을 시작하기 전에는 반드시 `git status`로 워킹 트리가 깨끗한지(clean) 먼저 확인하고, 수정 중인 로컬 변경 파일이 없을 때만 원격 최신 상태를 반영하기 위해 `git fetch`와 현재 브랜치의 `git pull`을 수행하여 충돌(Conflict)을 미연에 방지해야 한다. 만약 로컬에 아직 커밋되지 않은 변경 사항(Dirty working tree)이 있다면 임의로 git pull을 실행하지 말고 사용자에게 확인을 받거나 먼저 로컬 작업을 정리하라.
- 현재 브랜치가 main 또는 master 등 배포용 브랜치일 경우 직접 push 하지 않고, PR(Pull Request)을 생성하도록 권장하거나 사용자에게 다시 한번 경고해야 한다. 단, hotfix나 변경 사항이 3개 이하인 fix의 경우에는 묻지 않는다.



## 2. 커밋 분할 원칙 (Atomic Commits)
- 사용자가 커밋을 요청했을 때, 변경 사항이 서로 다른 성격(예: 신규 기능, 아키텍처 리팩토링, 버그 수정, 설정/도구 변경 등)을 포함하고 있다면 **절대로 한 번에 뭉뚱그려 커밋하지 말고 가능한 한 논리적 단위로 분할하여 커밋**한다.
- 분할된 각 커밋은 그 자체로 독립적이고 일관된 빌드 상태를 유지할 수 있어야 한다.

## 3. 커밋 메시지 작성 원칙 및 대화 맥락 추론 (Context-Driven Commit Message)
- **대화 맥락 기반 추론:** 커밋 메시지를 작성할 때 단순 `git diff`의 코드 변경점만 요약하지 않고, **사용자와 나눈 대화 내역(문제 제기 배경, 설계 의도, 결정 사항, 아키텍처 개선 이유 등)**을 면밀히 분석하여 커밋의 제목과 본문에 반영한다.
- 모든 커밋 메시지는 반드시 아래의 Conventional Commits 규격을 준수하여 작성한다.
- 모든 커밋 메시지는 반드시 **제목(Subject)**과 **본문(Description)**을 빈 줄 하나로 분리하여 작성한다.
- 모든 커밋 메시지의 제목과 본문은 한국어로 작성하도록 한다.
1. **제목 (Subject):** 50자 이내로 변경 사항을 요약한 단문 (Conventional Commits 규격 준수, 마침표 생략).
- commit message의 subject는 다음과 같이 작성한다.
  - 형식: `[type] <subject>`
    - `feat`: 새로운 기능 추가
    - `fix`: 버그 수정
    - `docs`: 문서 수정 (README 등)
    - `style`: 코드 포맷팅, 세미콜론 누락 등 (코드 변경 없음)
    - `refactor`: 코드 리팩토링
    - `test`: 테스트 코드 추가 및 수정
    - `chore`: 빌드, 도구 설정, 패키지 매니저 등 잡무
  - 예시: `[feat] 구글 로그인 추가`
  - 예시2: (subject가 여러 개인 경우) `[feat] SNS 로그인 추가, 게스트 로그인 추가`
2. **본문 (Description):** 제목 아래에 **반드시 빈 줄 하나를 비우고** 시작하며, 변경된 이유와 주요 내용을 글머리 기호(`-`)를 사용하여 상세히 기술한다.
- 제목을 포함한 예시: `
[feat] 구글 로그인 OAuth 연동 추가

- Google Cloud Console API 자격 증명 환경 변수 추가
- 로그인 성공 시 JWT 토큰 발급 및 클라이언트 리다이렉트 로직 구현
- 기존 구버전 로그인 버튼 컴포넌트 제거`

## 4. PROJECT_MAP.md 동기화 원칙
- 커밋하려는 변경 사항이 아래 항목 중 하나 이상에 해당하면, 반드시 `.agents/PROJECT_MAP.md`를 함께 갱신하여 커밋에 포함해야 한다:
  - 새로운 디렉터리 또는 논리 계층(Layer) 추가/삭제
  - 싱글턴 매니저 클래스 추가/제거/생명주기 변경
  - 계층 간 참조 방향 변경 또는 새로운 의존성 도입
  - `EventBus` 인터페이스(`ICharacterEvent` / `IPlayerEvent` 파생) 추가/삭제
  - 데이터 원본(SSOT) 위치 변경 (예: `ModLoader.*Database` → 다른 저장소)
  - 모딩 시스템 디렉터리 구조 또는 로딩 파이프라인 변경
  - 씬 전환 흐름(SubScene 추가/삭제/경로 변경) 변경
- 갱신 시 `PROJECT_MAP.md` 최상단의 `최종 갱신` 날짜를 커밋 시점으로 업데이트한다.
- PROJECT_MAP 갱신분은 해당 코드 변경 커밋에 함께 포함하며, 별도 커밋으로 분리하지 않는다.
